# AP02 — KI-Engine-Adapter (LLM-Gateway)
Quelle: GTO-Trainer_Gesamtscope.md, Abschnitt 7 · Stand: 2026-08-23 · Status: KANON (nicht editieren)

## Ziel
Stabiler, austauschbarer Zugang zur KI: CLI/Subscription primär, API-Fallback, Prompt-Template-System, Logging, Job-Anbindung.

## Baut auf / Hinterlässt
- **Baut auf:** AP1 — Deploy/HTTPS/Login, DB + Migrationen, `job_queue`- und `llm_call_log`-Tabellen (Skelett), `config`-Tabelle, Auth-Guard, Frontend-Shell mit API-Client, `packages/shared` als Vertragsort.
- **Hinterlässt für Folge-APs:** `LLMProvider` als **einziger** KI-Zugang (AP3 nutzt ihn für Vision/Chart-Digitalisierung, AP4 für Muster-Reports, AP5 für Didaktik/Bewertung, AP8 für HH-Analyse, AP9 für PDF-Texte/Kuration); Template-Registry; LLM-Job-Worker mit SSE-Statuskanal; Settings-UI mit Provider-/Modellwahl; vollständiges Call-Logging.

## Umgebung (verbindliche Vorgaben, als gegeben behandeln)
- Auf dem Host laufen **zwei getrennte Claude-CLI-Subscription-Profile** über separate Config-Verzeichnisse. Dieses Projekt verwendet **ausschließlich Profil B**: `CLAUDE_CONFIG_DIR=/home/phillip/.claude-b`.
- Das Default-Profil (`/home/phillip/.claude`) wird **nicht** gelesen, nicht verändert, nicht angefasst. Ein stiller Fallback auf das Default-Verzeichnis ist verboten — fehlt die Konfiguration, muss der Adapter mit klarer Meldung abbrechen.
- Das Backend läuft **im Container**, die Claude CLI mit ihrem Config-Verzeichnis liegt **auf dem Host**. Dieser Bruch ist in T2.1 explizit zu entscheiden und zu begründen (Architekturfrage, nicht Implementierungsdetail).
- Host-Besonderheiten aus AP1 gelten weiter: `NODE_ENV=production` in der Shell, Port 3000 fremd belegt, Backend auf 3010, Postgres auf 55434, kein GNU Make, Agent-Sitzung ohne Root (`NoNewPrivs=1`).

## Primärtasks (Reihenfolge fix, je Task ein Prompt)

### T2.1 Doku-Verifikation & Interface-Design
Ziel: Verbindlich klären, wie die CLI headless und aus dem Container heraus angesprochen wird, und das `LLMProvider`-Interface als Vertrag für alle Folge-APs festschreiben.
Subtask-Kern:
- Aktuelle Claude-Code-Doku (headless-Aufruf, Auth, Session-/Kontextverhalten, Output-Format, Limits) prüfen; Ergebnis + gewählte Aufrufform in DECISIONS.md festhalten.
- `LLMProvider`-Interface in `packages/shared` definieren: `complete(request: {system, messages, model, maxTokens, json_schema?}) → {text|json, meta}`; Fehler-Taxonomie (Timeout, Limit, Auth, Transient).
- **Zusätzlich (Umgebungsvorgabe):** Container-zu-Host-Zugriff auf die CLI entscheiden und begründen (Optionen u. a.: CLI im Backend-Image plus Read-Mount des Profil-B-Verzeichnisses, oder ein Host-seitiger Aufrufweg). Kriterien: Funktioniert es im Compose-Betrieb? Bleibt Profil B isoliert? Ist es ohne Root betreibbar?
AK-Kern: Interface liegt in `packages/shared` und deckt Request/Response/Fehler-Taxonomie ab; DECISIONS.md enthält ADRs zu Aufrufform und Container-Zugriff mit belegten Doku-Aussagen; Vision-Fähigkeit (Bild-Input) ist im Interface berücksichtigt, da AP3 sie zwingend braucht.

### T2.2 Adapter A: Claude-CLI (Subscription)
Ziel: Produktiv nutzbarer CLI-Adapter gegen Profil B, robust gegen Timeouts, Parsing-Fehler und transiente Störungen.
Subtask-Kern:
- Headless-Aufruf implementieren (Prozess-Spawn, stdin/stdout, Timeout, sauberes Kill), strukturierte Ausgabe erzwingen (JSON-Modus, robustes Parsen inkl. Fence-Stripping).
- Nebenläufigkeitslimit (Semaphore), Retry mit Backoff für transiente Fehler.
- **Profil-Bindung (Umgebungsvorgabe):** `CLAUDE_CONFIG_DIR` als Pflicht-Konfiguration in `.env`/`.env.example`; beim Spawn explizit ins Prozess-Environment setzen; kein Fallback auf das Default-Profil; Startvalidierung mit klarer Fehlermeldung bei fehlendem/ungültigem Wert.
AK-Kern: Live-Aufruf gegen Profil B nachweislich erfolgreich; Beleg, dass `CLAUDE_CONFIG_DIR` beim Spawn tatsächlich gesetzt ist; Timeout- und Parsing-Fehlerpfade getestet; Verhalten bei fehlender Konfiguration = sauberer Abbruch, kein Default-Profil-Zugriff.

### T2.3 Adapter B: Anthropic Messages API (Fallback)
Ziel: Gleichwertiger zweiter Adapter, damit das Tool von der Subscription-Nutzung nicht abhängt (Risiko R1 im Gesamtscope).
Subtask-Kern:
- API-Adapter mit identischem Interface; Provider-Umschaltung rein per Konfiguration; Verhaltens-Paritätstests beider Adapter (gemockte Ebene + 1 Live-Smoke je Adapter, überspringbar per Flag).
AK-Kern: Paritätstests grün (gleiche Eingabe → strukturell gleiche Antwortform und gleiche Fehler-Taxonomie bei beiden Adaptern); Umschaltung nachweislich ohne Codeänderung; Live-Smoke je Adapter ausgeführt oder Auslassung dokumentiert begründet.

### T2.4 Prompt-Template-System
Ziel: Versionierte, testbare Prompt-Bausteine statt verstreuter Inline-Strings — Grundlage der Didaktik-Qualität ab AP5.
Subtask-Kern:
- Template-Registry (Datei-basiert, versioniert): Platzhalter, Partials (z. B. "Antworte als JSON gemäß Schema"), zentrale System-Prompts (Lehrer-Persona, Bewertungs-Persona, Analyse-Persona).
- Golden-Tests: Template + Beispiel-Input → erwarteter gerenderter Prompt.
AK-Kern: Registry lädt Templates aus Dateien, unbekannte Platzhalter erzeugen Fehler statt stiller Lücken; die drei Personas existieren; Golden-Tests grün.

### T2.5 Job-Queue-Worker & Logging
Ziel: Lange KI-Aufgaben laufen asynchron und beobachtbar — Voraussetzung für die Chart-Digitalisierung in AP3.
Subtask-Kern:
- Worker-Prozess für LLM-Jobs (DB-Queue aus AP1): claim, run, retry, dead-letter; SSE-Statuskanal zum Frontend.
- Vollständiges `llm_call_log`-Schreiben; Admin-Ansicht "letzte KI-Aufrufe" (einfach) im Frontend unter Einstellungen.
AK-Kern: Job durchläuft nachweislich claim → run → done; Fehlerfall führt nach `max_attempts` in Dead-Letter statt Endlosschleife; `llm_call_log` enthält Provider, Modell, Dauer und Status; SSE liefert Statusänderungen; Admin-Ansicht zeigt echte Einträge.

### T2.6 Modell-/Provider-Einstellungen
Ziel: Provider und Modell zur Laufzeit umschaltbar, mit sofortiger Verifikationsmöglichkeit (F28).
Subtask-Kern:
- Settings-UI: Provider (CLI/API), Modell (Opus/Sonnet), Timeouts; serverseitige Validierung; Ping-Test-Button ("Testaufruf ausführen").
AK-Kern: Umschaltung wird persistiert (config-Tabelle) und wirkt ohne Neustart; ungültige Werte werden serverseitig abgelehnt; Ping-Test liefert im Erfolgsfall die Antwort samt Provider/Modell/Dauer und im Fehlerfall eine verständliche Meldung; Route ist auth-geschützt.

## Scope-Delta
1. **Profil-B-Bindung ergänzt (T2.1/T2.2):** Der Gesamtscope kennt nur "die Claude CLI". Auf dem Zielhost existieren zwei Subscription-Profile; verbindlich ist `CLAUDE_CONFIG_DIR=/home/phillip/.claude-b`. Auswirkung: zusätzliche Pflicht-Konfiguration und Verifikationspflicht beim Spawn; keine inhaltliche Änderung am Interface.
2. **Container-zu-Host-Zugriff als expliziter Entscheidungspunkt in T2.1 ergänzt:** Im Gesamtscope nicht adressiert, da dort das Deployment-Detail aus AP1 noch nicht feststand. Auswirkung: eine zusätzliche ADR-Pflicht in T2.1; potenziell Anpassung von Dockerfile/Compose innerhalb von T2.2.
3. **Vision-Fähigkeit im Interface (T2.1):** Der Gesamtscope nennt in T2.1 nur Text-Requests, verlangt aber in T3.3 Vision-Aufrufe über den `LLMProvider`. Das Interface muss daher von Anfang an Bild-Input vorsehen. Auswirkung: Vermeidung eines Interface-Bruchs in AP3.
4. **Statusbericht-Dateiname zweistellig:** `docs/status/AP02.md` (Konvention aus PK_AP_TEMPLATE Regel 4), analog zu AP1.
