## Primärtasks (Reihenfolge fix, je Task ein Prompt)

### T1.1 Repo & Projektgerüst
Ziel: Leeres Repo wird zum strukturierten, lint-/testbaren Monorepo inkl. vollständigem Doku- und Datenverzeichnis-Gerüst.
Subtask-Kern:
- Monorepo anlegen (pnpm workspaces): `apps/backend` (Fastify+TS), `apps/frontend` (React+Vite+TS), `packages/shared` (Typen/Verträge).
- Lint/Format (ESLint, Prettier), tsconfig strikt, Test-Runner (Vitest) einrichten.
- `docs/`-Gerüst anlegen: ARCHITECTURE.md, DECISIONS.md, INTERFACES.md, RUNBOOK.md, status/, ap/ (Ablageort der kanonischen Arbeitspaket-Dateien `AP<NN>.md`, vom Nutzer eingespielt, vom Agenten nur gelesen), AGENT_GUIDE.md (Arbeitsregeln des Coding-Agenten inkl. Kontext- und Doku-Pflichten aus Gesamtscope Abschnitt 2).
- Makefile/NPM-Scripts: dev, test, build, lint.
- **Datenverzeichnis-Konvention:** `data/book-source/` (git-ignoriert, nicht versioniert) als fest definierter Eingabeordner für die rohen Buchquellen (MD-Datei + Chart-Bilder) anlegen, in INTERFACES.md als Pflicht-Input für AP3 dokumentieren, `data/book-source/README.md` mit Anleitung für den Nutzer ("hier die Buch-MD + Bilder ablegen, exakte erwartete Struktur: …") erzeugen. Wird erst in AP3 gelesen, muss aber spätestens vor Start von AP3 befüllt sein.
AK-Kern: `pnpm install` + `pnpm lint` + `pnpm test` + `pnpm build` laufen fehlerfrei; alle genannten docs-Dateien und Verzeichnisse existieren; `data/book-source/` ist git-ignoriert, README aber versioniert.

### T1.2 Datenbank & Migrationen
Ziel: Lauffähige PostgreSQL-Instanz mit versioniertem Migrationssystem und den Basistabellen.
Subtask-Kern:
- PostgreSQL via Docker Compose; Migrations-Tooling (Drizzle ORM oder Prisma — Entscheidung in DECISIONS.md begründen).
- Basistabellen: user, session, config, llm_call_log (Skelett), job_queue.
- Seed-Skript + DB-Reset-Skript für Entwicklung.
AK-Kern: Migration von leerer DB läuft durch und erzeugt alle 5 Tabellen (Nachweis via Tabellen-Listing); Seed und Reset laufen fehlerfrei; DECISIONS.md enthält den ORM-Entscheid mit Begründung.

### T1.3 Auth & Single-User-Login
Ziel: Sicherer Single-User-Login als Zugangsschutz für alles Weitere.
Subtask-Kern:
- Passwort-Hashing (argon2), Login/Logout, HTTP-only-Session-Cookie, CSRF-Schutz, Login-Rate-Limit.
- CLI-Skript zum Setzen/Ändern des Passworts; optionaler TOTP-Hook vorbereiten (Flag, Default aus).
AK-Kern: Integrationstests decken ab: erfolgreicher Login, falsches Passwort, Rate-Limit greift, geschützte Route ohne Session → 401; Passwort-CLI-Skript nachweislich funktionsfähig.

### T1.4 Frontend-Shell
Ziel: Bedienbare Frontend-Hülle mit Login-Screen, Navigation und funktionierendem API-Client.
Subtask-Kern:
- React-App mit Router, Login-Screen, leeres Dashboard, Layout (Sidebar: Lernen · Drills · Turniere · Material · Einstellungen), Dark-Mode-fähiges Design-Token-Set.
- API-Client mit Session-Handling und Fehleranzeige.
AK-Kern: Frontend baut fehlerfrei; Login gegen echtes Backend erfolgreich, danach Dashboard sichtbar; alle 5 Sidebar-Routen erreichbar (Platzhalterseiten); 401 führt zu sauberem Redirect auf Login.

### T1.5 Deployment & HTTPS
Ziel: App läuft containerisiert auf dem Server hinter dem Host-Nginx, erreichbar und gesichert; Backup/Restore erprobt.
Subtask-Kern:
- Docker Compose (backend, frontend-static, postgres) auf dem Host; Ports intern, kein eigener Reverse-Proxy-Container (Host-Nginx übernimmt das).
- Host-Nginx-vhost-Konfig für `gto.growento.com` (Reverse Proxy auf die Compose-Ports) als Datei im Repo (`deploy/nginx/gto.growento.com.conf`) + Anleitung zum Einspielen auf den Host (Symlink/Copy nach `/etc/nginx/sites-available`, `nginx -t`, reload).
- **DNS-Gate — zweistufig:**
  1. **Stufe A** (unabhängig von DNS): App per Docker Compose + Host-Nginx über HTTP und/oder Server-IP:Port erreichbar machen; `/healthz` darüber verifizieren.
  2. **Stufe B** (setzt voraus, dass der A-Record von `gto.growento.com` bereits auf die Server-IP zeigt): Zertifikat per vorhandenem Certbot ausstellen (`certbot --nginx -d gto.growento.com`), vhost auf HTTPS + Redirect umstellen.
  - Ist die DNS bei Ausführung noch nicht propagiert: Stufe A abschließen, Ergebnisbericht als BLOCKED-auf-Stufe-B markieren mit exakter Anleitung für den nächsten Queue-Lauf, statt den ganzen Task/AP zu blockieren.
- Deploy-Skript (Build → Server), `.env`-Schema dokumentiert; Healthcheck-Endpoint `/healthz`.
- Backup-Skript (pg_dump + Assets, Rotation) + dokumentierter Restore-Test.
AK-Kern: `docker compose up` bringt alle Container in Healthy-Status; `/healthz` liefert 200 über den Host-Nginx (Stufe A belegt via curl-Ausgabe); HTTPS aktiv **oder** sauber als BLOCKED-auf-DNS dokumentiert; Backup erzeugt Dump und Restore-Test protokolliert.

### T1.6 CI-Basics & Abschluss
Ziel: Automatisierte Qualitätsschranke plus erster durchgehender E2E-Nachweis; AP-Abschlussdokumentation.
Subtask-Kern:
- GitHub-Actions (oder lokales Pre-Push-Skript): lint + test + build als Pflicht.
- Smoke-E2E: Login → Dashboard erreichbar (Playwright, 1 Test).
- Statusbericht `docs/status/AP01.md`.
AK-Kern: CI-Lauf (bzw. Pre-Push-Skript) endet grün mit lint+test+build; Playwright-Smoke-Test läuft durch (Ausgabe im Bericht); `docs/status/AP01.md` existiert und fasst AP1 vollständig zusammen inkl. HTTPS-Status.

## Standard-Subtasks (gelten für jeden Task, nicht wiederholt)
Tests · Doku-Deltas (ARCHITECTURE/INTERFACES/DECISIONS) · Statusbericht `docs/status/AP01.md` · Commit `AP1.T<M>: <summary>`

## Definition of Done (AP)
Deploy auf Server erfolgreich (mind. Stufe A: erreichbar über IP/HTTP hinter Host-Nginx); Login funktioniert; alle Tests grün; RUNBOOK enthält Deploy+Backup+Restore; Statusbericht liegt vor und vermerkt HTTPS-Status (aktiv, oder BLOCKED-auf-DNS mit Anleitung).

## Scope-Delta
1. **Statusbericht-Dateiname zweistellig:** Der Gesamtscope nennt in T1.6 `docs/status/AP1.md`. Verwendet wird stattdessen **`docs/status/AP01.md`**, konsistent zur zweistelligen AP-Dateinamens-Konvention aus PK_AP_TEMPLATE (Regel 4). Auswirkung: rein kosmetisch/Sortierstabilität; gilt analog für alle Folge-APs.
2. **Reihenfolge-Hinweis AP-Datei:** Da das Repo zu AP1-Beginn leer ist, kann `docs/ap/AP01.md` erst nach T1.1 committet werden (das Verzeichnis entsteht dort). Die in PK_PROMPT_TEMPLATE vorgeschriebene Kanon-Prüfung gegen diese Datei entfällt daher ausschließlich für T1.1 und gilt ab T1.2 regulär. Auswirkung: keine inhaltliche Abweichung, nur zeitliche Verschiebung um einen Task.
