## 2. Schnittstellen, auf denen AP3 aufsetzt

**Job-Typ registrieren** (`docs/INTERFACES.md` Abschnitt 10) — für die
Chart-Batchjobs:

```ts
const chartJob: JobType<ChartPayload> = {
  type: 'chart.digitize',
  parsePayload(raw) { /* wirft JobPayloadError → sofort Dead-Letter */ },
  async run(payload, ctx) { /* rendert Template, ruft Provider, schreibt Ergebnis */ },
};
// in apps/backend/src/jobs/runtime.ts:
new JobHandlerRegistry().register(createLlmCompleteJob({…})).register(chartJob);
```

Einplanen mit `enqueueJob(db, { jobType: 'chart.digitize', payload, maxAttempts })`.
Retry, Dead-Letter, Protokoll und SSE kommen automatisch — ein Handler baut
**keinen** eigenen Retry.

**Template anlegen und rendern** (Abschnitt 9): `.md`-Datei unter
`apps/backend/prompts/task/` mit JSON-Kopfdaten (`id`, `version`, `kind`,
`system`, `placeholders`, optional `jsonSchema`), dann

```ts
const request = templates.renderRequest('task/chart-digitize', werte, { model, maxTokens });
```

Fehlende oder unbekannte Platzhalter sind Fehler, keine Lücken. Jedes neue
Template braucht einen Golden-Fall, sonst wird die Suite rot.

**Vision-Requests** laufen über denselben Provider: Ein Bild ist ein
Nachrichtenbaustein
`{ type: 'image', mediaType: 'image/png', data: <base64 ohne data:-Präfix> }`.
Der CLI-Adapter setzt das über `--input-format stream-json` um (in T2.1 gegen
die echte CLI verifiziert), der API-Adapter als Base64-Block. Im Protokoll
erscheinen Bilder **nie** im Klartext, sondern als Kurzvermerk mit Größe.

**Chart-Batchjobs** docken damit so an: je Chart ein `chart.digitize`-Job,
Nebenläufigkeit über `llm.max_concurrency` (Default 2) begrenzt, Fortschritt
über SSE, Fehlerbilder in `llm_call_log` und im Dead-Letter.

## 5. Offene Punkte und Risiken

- **Der API-Live-Smoke ist offen** — es liegt kein Anthropic-API-Schlüssel vor.
  Adapter B ist gegen einen gemockten Endpunkt vollständig geprüft, aber nie
  gegen die echte API gelaufen. Nachholen:
  `ANTHROPIC_API_KEY=sk-ant-… LLM_LIVE_SMOKE=true pnpm --filter @gto/backend exec vitest run test/llm/live-smoke.test.ts`
- **Kontingentverbrauch bei Massenaufrufen:** AP3 setzt rund 336 Chart-Aufrufe
  ab. Bei Sonnet ist das ein spürbarer Teil des Subscription-Kontingents; ein
  Session- oder Wochenlimit bringt die Charge zum Stillstand (Kategorie
  `rate_limit`, Wiedervorlage über die Job-Queue). Vor dem Start Modell und
  `llm.max_concurrency` bewusst wählen und mit einer kleinen Charge messen.
- **Host-Runner startet nach einem Reboot nicht automatisch** (RUNBOOK 9.2).
  Ohne ihn scheitert jeder CLI-Aufruf mit Kategorie `auth`.
- **vhost inklusive SSE-`location` ist nicht eingespielt** — Root nötig
  (RUNBOOK 8.4, 10.4). Ohne ihn puffert Nginx den Statuskanal.
- **Eine Backend-Instanz vorausgesetzt:** Das Job-Claiming ist mehrinstanzfähig,
  der SSE-Ereignisbus ist prozessintern (ADR-0026).
- **Token-Grenzen zum Template passend wählen:** Die Claude CLI kürzt nicht,
  sondern bricht ab. Zu knappes `maxTokens` ergibt Kategorie `invalid` — in
  T2.6 beim Ping-Test reproduziert und behoben.
- `/home/phillip/.claude-b` ist weiterhin `drwxr-xr-x`; `chmod 700` steht aus.
- Offene AP1-Punkte gelten weiter (vhost/TLS erfordern Root).
