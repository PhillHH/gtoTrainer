## 2. Was nach T2.2 existiert (Adapter A)

`apps/backend/src/llm/` — Implementierung von `LLMProvider` gegen Profil B:

- **Prozessstart ohne Shell**, Argumente als Array, Prompt ausschließlich über
  stdin. Das Environment des Kindprozesses ist eine Allowlist aus vier
  Variablen; `ANTHROPIC_API_KEY` bleibt bewusst draußen, sonst würde die CLI
  am Subscription-Profil vorbei abrechnen.
- **Timeout je Aufruf**, Abbruch erst per SIGTERM, dann SIGKILL, jeweils auf die
  ganze Prozessgruppe — es bleibt kein Prozess zurück.
- **Robustes Parsen**: letzte `type: "result"`-Zeile des NDJSON-Stroms,
  `structured_output`, sonst Fence-Stripping und Wrapper-Text-Extraktion, dann
  Schemaprüfung. Erfolg hängt an `is_error` und Exit-Code, nicht an `subtype`.
- **Fehler-Taxonomie** vollständig belegt; unbekannte Fehler gelten als **nicht**
  wiederholbar.
- **Semaphore** (`LLM_MAX_CONCURRENCY`, Default 2) und **Retry mit Backoff plus
  Streuung** nur für retrybare Kategorien, mit hartem Gesamtbudget.
- **Host-Runner** (`pnpm llm:runner`) als Umsetzung von ADR-0022.

Neue Entscheidungen aus der Umsetzung stehen in **ADR-0023**: einheitlicher
`--input-format stream-json`-Aufruf, `--system-prompt` plus `--tools ""`,
Environment-Allowlist, Semaphore-/Retry-Parameter, Schemaprüfung ohne neue
Dependency. **Keine neuen Dependencies in T2.2.**

### Gemessen bei der Umsetzung

| Beobachtung                                                               | Folge                                                     |
| ------------------------------------------------------------------------- | --------------------------------------------------------- |
| `--tools ""` senkt die Eingabe von `cache_creation 18543` auf `input 247` | Werkzeuge sind aus; `--json-schema` funktioniert trotzdem |
| CLI lehnt `--input-format stream-json` mit `--output-format json` ab      | Ausgabe durchgängig `stream-json`                         |

| Container läuft als uid 1000 wie `phillip`                                | Socket-Mode `0600` genügt, read-only-Mount reicht         |

## 3. Container-Betrieb

`docker-compose.yml` hängt **nur** das Socket-Verzeichnis des Runners ein
(`/run/gto-llm:ro`) und setzt `LLM_TRANSPORT=socket`. Das
Profil-B-Verzeichnis wird nicht gemountet, `CLAUDE_CONFIG_DIR` ist im Container
nicht gesetzt. Am `apps/backend/Dockerfile` war keine Änderung nötig — genau
das war der Zweck von ADR-0022.

Nachgewiesen: echter Aufruf aus `gto-backend` heraus über den Host-Runner,
Antwort `OK`, Modell `claude-haiku-4-5`, 3628 ms, Exit 0.

## 3a. Was nach T2.3 existiert (Adapter B und Registry)

- **`AnthropicApiProvider`** gegen die Messages API über das offizielle SDK
  (`@anthropic-ai/sdk`, einzige neue Dependency, ADR-0024). Der SDK-eigene
  Retry ist abgeschaltet, damit es genau **eine** Wiederholungslogik gibt.
- **`GuardedProvider`** (`base-provider.ts`): Semaphore, Retry und
  Vorprüfung liegen jetzt an einer Stelle; beide Adapter erben sie und
  implementieren nur noch `attempt()`. Die T2.2-Tests liefen nach der
  Umstrukturierung unverändert weiter grün.
- **`LlmProviderRegistry`**: der einzige Weg zu einem Provider. Wahl aus der
  `config`-Tabelle (`llm.provider`) → `LLM_PROVIDER` → `cli`, bei jedem Aufruf
  neu gelesen. Ein unbekannter Wert ist ein Fehler, kein stiller Default.
- **Strukturierte Ausgabe** über `output_config.format`; Schemata bekommen
  rekursiv `additionalProperties: false`, damit derselbe Request bei beiden
  Adaptern läuft. Ausgewertet wird mit denselben Funktionen wie beim
  CLI-Adapter — gleiche Eingabe, gleicher `parse`-Fehler.
- **API-Schlüssel:** Pflicht nur bei aktivem API-Provider. Ohne Schlüssel
  startet das Backend mit `cli` normal; wird `api` aktiv, bricht der Bau des
  Adapters mit Kategorie `auth` ab. Der Schlüssel wird nirgends ausgegeben.

## 3b. Was nach T2.4 existiert (Prompt-Template-System)

Prompts sind ab jetzt versionierte Dateien unter `apps/backend/prompts/`, keine
Inline-Strings. Im Container liegen sie unter `/app/prompts` (`PROMPTS_DIR`) —
dieselbe Mechanik wie bei den Migrationen.

| Bereich    | Inhalt                                                                |
| ---------- | --------------------------------------------------------------------- |
| `partial/` | `language`, `data-truth`, `json-output` — wiederverwendbare Bausteine |
| `persona/` | `teacher`, `grader`, `analyst` — die drei System-Personas             |
| `task/`    | `concept-explanation` — Beispielaufgabe, die alles zusammenführt      |

- **Kopfdaten als JSON-Block** am Dateianfang: Kennung, Version, Art, Zweck,
  Platzhalter, optional das `jsonSchema` (ADR-0025). Ohne Dependency parsbar.
- **Strikte Platzhalter:** fehlender Wert → Fehler, unbekannter Wert → Fehler.
  Eingesetzte Werte werden literal übernommen und nicht erneut als Template
  gelesen — Buchtext kann die Prompt-Struktur nicht verändern.
- **Partials werden beim Laden eingesetzt**, verschachtelbar, gegen Zyklen und
  eine Tiefe über 10 Ebenen abgesichert. Alle drei Personas binden
  `partial/language` und `partial/data-truth` ein.
- **`renderRequest()` liefert einen fertigen `LlmRequest`** — System-Prompt aus
  der Persona, Aufgabenrumpf als Nachricht, `jsonSchema` aus den Kopfdaten. Der
  Aufrufer baut keine Strings mehr zusammen.
- **Golden-Tests** halten jeden gerenderten Prompt fest. `pnpm prompts:golden`
  schreibt sie bewusst neu; in der CI ist der Modus gesperrt. Ein Abdeckungstest
  erzwingt, dass jedes Template einen Golden-Fall hat.

**Keine neuen Dependencies in T2.4.**

## 3c. Was nach T2.5 existiert (Worker, Protokoll, Statuskanal)

- **Job-Worker** als Schleife im Backend-Prozess (ADR-0026) — kein zweiter
  Container, kein Broker. Abschaltbar über `WORKER_ENABLED=false`.
- **Atomares Claiming** mit `FOR UPDATE SKIP LOCKED`: ein Job geht auch bei
  zehn gleichzeitigen Versuchen an genau einen Worker. `attempts` steigt beim
  Holen, damit ein Absturz mitzählt; ein Job, der länger als
  `WORKER_STALE_AFTER_MS` (Default 5 min) in `running` hängt, wird wieder
  aufgenommen (ADR-0027).
- **Retry und Dead-Letter** anhand der Taxonomie aus T2.1: nur retrybare
  Kategorien werden erneut eingeplant, mit Backoff über `available_at`; danach
  `dead` mit gespeichertem `last_error`. `POST /api/jobs/:id/retry` plant einen
  toten Job erneut ein.
- **Handler-Registry**: der Worker kennt keine Fachlichkeit. Ein Referenz-Job
  (`llm.complete`) belegt das Zusammenspiel von Queue, Template-Registry und
  Provider-Registry; AP3/AP4/AP8/AP9 hängen sich nach demselben Muster ein.
- **Zentrales Aufruf-Protokoll**: `withCallLog` sitzt in der Provider-Registry
  und umfasst jeden Adapter — kein Aufrufer kann es vergessen. Fehlschläge
  werden genauso protokolliert; ein Fehler beim Protokollieren lässt den Aufruf
  nie scheitern. Bilder erscheinen als Kurzvermerk, lange Inhalte werden
  sichtbar gekürzt (ADR-0028).
- **SSE-Statuskanal** `GET /api/jobs/events`, auth-geschützt, mit Keepalive und
  sauberem Aufräumen bei Abbruch und Herunterfahren. Der vhost im Repo hat eine
  eigene `location` ohne Pufferung.
- **Ansicht „letzte KI-Aufrufe"** unter Einstellungen: Liste, Statusfilter,
  Detailansicht, Live-Aktualisierung über SSE. Sie ersetzt die Platzhalterseite.

**Keine neuen Dependencies in T2.5.**

## 5. Offene Punkte

- Der Runner startet nach einem Reboot nicht automatisch. Der root-freie Weg
  (`@reboot` in der Benutzer-Crontab) ist beschrieben, aber weder eingerichtet
  noch verifiziert — die Crontab war in der Agenten-Sitzung nicht lesbar.
- Der Adapter ist **nicht** an Job-Queue, `llm_call_log` oder UI angebunden
  (T2.5/T2.6), und es gibt noch keine HTTP-Route dafür.
- Mehrstufige Verläufe werden in **eine** Nachricht gefaltet: Der
  Streaming-Input der CLI kennt keine Assistant-Turns. Für die einstufigen
  Aufrufe von AP3–AP9 ist das ohne Belang, für einen echten Chat wäre es zu
  knapp.
- `/home/phillip/.claude-b` ist weiterhin `drwxr-xr-x`; `chmod 700` steht aus.
- **Der Live-Smoke des API-Adapters ist offen**, weil kein Anthropic-API-Key
  vorliegt. Er wird sichtbar übersprungen, nicht als bestanden gemeldet.
  Nachholen mit:
  `ANTHROPIC_API_KEY=sk-ant-... LLM_LIVE_SMOKE=true pnpm --filter @gto/backend exec vitest run test/llm/live-smoke.test.ts`
  Der API-Adapter ist damit gegen einen gemockten Endpunkt geprüft, aber noch
  nie gegen die echte API gelaufen.
- Die API lehnt Schemata mit `minimum`, `$ref` oder Rekursion ab (400 →
  `invalid`); der CLI-Adapter ist hier toleranter. Für AP3–AP9 ohne Belang,
  aber eine echte Abweichung zwischen den Adaptern.
- Templates enthalten bewusst **keine** Fachdaten; die kommen ab AP3 als
  Platzhalterwerte aus der Datenbank. Ob das in der Praxis trägt, zeigt sich
  erst mit den echten Lern-Templates in AP5.
- Die SSE-`location` im vhost ist vorbereitet, aber wie der ganze vhost noch
  nicht eingespielt (Root nötig, RUNBOOK 10.4). Ohne sie puffert Nginx den
  Strom, und die Live-Aktualisierung bleibt stehen.
- Das Betriebsmodell setzt **eine** Backend-Instanz voraus: Das Claiming ist
  mehrinstanzfähig, der SSE-Ereignisbus ist es nicht (ADR-0026).
- Beim Echtlauf lag eine Aufrufdauer deutlich über der Timeout-Obergrenze des
  Runners (498 s statt 120 s), allerdings während mehrere Testaufrufe
  gleichzeitig liefen. Eine gezielte Nachmessung bestätigte die Abbruchmechanik
  (5 s Vorgabe → SIGKILL nach 7,5 s, `timedOut: true`). Unter Last im Auge
  behalten, spätestens wenn AP3 hunderte Aufrufe absetzt.
- Das Beispieltemplate aus T2.4 erzeugt auf Haiku lange Antworten; mit knappem
  `maxTokens` bricht die CLI ab (Kategorie `invalid`). Für AP5 heißt das:
  Token-Grenzen zum Template passend wählen.
- Offene AP1-Punkte gelten weiter (vhost/TLS erfordern Root).
