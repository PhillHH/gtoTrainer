## 4. Was technisch abgesichert ist (nicht nur beschrieben)

Zwölf Invarianten, alle über Constraints oder Trigger — die Liste steht in
[INTERFACES.md 17](../INTERFACES.md). Die drei, die am meisten tragen:

- **Ereignisse sind unveränderlich.** Zwei Trigger weisen UPDATE und DELETE

## 7. Was nach T4.2 existiert

Der Lernstand hat **eine** Schreibstelle. Ab hier erzeugt kein Modus mehr
selbst abgeleiteten Zustand — er meldet ein Ereignis, und der Rest folgt
daraus.

| Baustein                                     | Ort                                          |
| -------------------------------------------- | -------------------------------------------- |
| Ereignis-Vertrag, Nutzdaten je Typ, Prüfung  | `packages/shared/src/learning.ts`            |
| Ableitungen (reine Funktionen, intern)       | `apps/backend/src/learning/derive.ts`        |
| `recordLearningEvent`, `replayLearningState` | `apps/backend/src/learning/service.ts`       |
| `POST /api/learning/events`                  | `apps/backend/src/learning/routes.ts`        |
| Kommando `pnpm learning:replay`              | `apps/backend/src/learning/cli-replay.ts`    |
| Umgehungsverbot als Lint-Regel               | `eslint.config.js` (`no-restricted-imports`) |

### Der Ablauf

1. **Validierung** — Ereignistyp, Nutzdaten, Konzept, Korrekturbezug. Ablehnung
   feldweise; es wird nichts geschrieben.
2. **Persistenz** — `insert … on conflict (id) do nothing`. Keine Zeile zurück
   heißt: die ID gab es schon, `status: 'duplicate'`, kein Fehler.
3. **Ableitung** — Mastery, Queue, Fehlerlog und Rating werden aus dem Strom
   neu berechnet.
4. **Alles in einer Transaktion.**

### Die Entscheidung, die alles trägt

Die Ableitung rechnet **den ganzen Ereignisstrom des Konzepts neu**, statt ein
Delta zu addieren ([ADR-0040](../DECISIONS.md)). Damit rufen der inkrementelle
Weg und der Replay denselben Code — die vom DoD geforderte Gleichheit ist eine
Eigenschaft der Konstruktion, keine Hoffnung, die ein Test bewacht. Der Preis
ist Rechenaufwand, der bei Single-User-Betrieb nicht ins Gewicht fällt.

Daraus folgen drei Nebenbedingungen, die im Code sichtbar sind: alle
Zeitstempel abgeleiteter Zeilen stammen aus den Ereignissen, `error_log.id`
**ist** die Ereignis-ID, und eine Rating-Achse ohne Ereignisse wird nicht
angefasst.

### Determinismus — als Test, nicht als Zusage

Keine Ableitung benutzt Systemzeit, Zufall oder die Datenbank. Das einzige
`new Date(...)` in `derive.ts` rechnet auf `occurredAt` weiter.
`test/learning/determinism.test.ts` liest das Modul und weist verbotene Aufrufe
nach — die Regel gilt bindend für T4.3 bis T4.5 und fällt dort auf, wenn sie
gebrochen wird.

### Platzhalter, die T4.3 bis T4.6 ersetzen

| Funktion             | Fassung in T4.2                                                      | Ersetzt in |
| -------------------- | -------------------------------------------------------------------- | ---------- |
| `foldConceptMastery` | Score = Mittel der Ergebnisse, Konfidenz = Anteil objektiver Signale | T4.3       |
| `foldReviewQueue`    | Eintrag ab dem ersten Fehlschlag, fällig einen Tag später            | T4.4       |
| `foldSkillRating`    | Mittel der Ergebnisse des Themenbereichs                             | T4.5       |
| `foldErrorLog`       | Eintrag je Ergebnis < 0,5; Schweregrad `high` bei 0, sonst `medium`  | T4.6       |

Die Zähler je Signalklasse, `repetitions`, `lapses` und der Ursprung des
Queue-Eintrags werden schon jetzt vollständig geführt. T4.3 und T4.4 tauschen
den Rumpf der jeweiligen Funktion — die Verdrahtung bleibt unberührt.

### Umgehungsverbot

Verbindlich in INTERFACES.md 18, technisch unterstützt durch eine
ESLint-Regel: Ein Import von `learning/derive.js` außerhalb von
`src/learning/` wird abgewiesen. Nach außen sichtbar sind nur
`recordLearningEvent`, `replayLearningState`, `seedLearningState`,
`resetLearningState` und `countLearningRows`.

## 8. Was nach T4.3 existiert

Die erste der vier Ableitungen hat ihre endgültige Form. Der Platzhalter aus
T4.2 wurde **an derselben Schnittstelle** ersetzt — der Service hat davon
nichts mitbekommen.

| Baustein                                 | Ort                                                       |
| ---------------------------------------- | --------------------------------------------------------- |
| Score, Konfidenz, Weiterschaltung (rein) | `apps/backend/src/learning/mastery.ts`                    |
| Verdrahtung (Ereignisse → Signale)       | `apps/backend/src/learning/derive.ts`                     |
| Abruf gegen echte Daten                  | `evaluateConceptAdvance` in `service.ts`                  |
| Ermittlung der Anker-Möglichkeit         | `objectiveAnchorsPossible` in `service.ts`                |
| Schwellen lesen und ändern               | `readLearningThresholds`, `updateLearningThresholds`      |
| Kommando `pnpm learning:thresholds`      | `apps/backend/src/learning/cli-thresholds.ts`             |
| Entscheidungs-Vertrag für AP5/AP6        | `packages/shared/src/learning.ts`                         |
| Migration (Schwelle 0,8 → 0,75)          | `apps/backend/drizzle/0009_mastery_threshold_default.sql` |

### Die Formel

```
          PRIOR_SCORE · PRIOR_WEIGHT + Σ wᵢ · outcomeᵢ
  score = -------------------------------------------      PRIOR_SCORE = 0
                    PRIOR_WEIGHT + Σ wᵢ                     PRIOR_WEIGHT = 1

  wᵢ = Signalgewicht · Schwierigkeit · Aktualität · (Fehler? 1,5 : 1)

  confidence = 1 − e^(−Σ Konfidenz-Gewicht · Aktualität / 4)
```

| Signalklasse    | Score-Gewicht | Konfidenz-Gewicht |
| --------------- | ------------- | ----------------- |
| `objective`     | 1,0           | 1,0               |
| `ai_judged`     | 0,5           | 0,2               |
| `self_reported` | 0,2           | 0,05              |

**Zwei Gewichtstabellen, und darin liegt der Kern.** Die eine sagt, _wie weit_
ein Signal den Score bewegt, die andere, _wie sehr_ es die Aussage festnagelt.
Der Fehler einer KI-Bewertung ist **korreliert** — ist das Modell zu freundlich,
ist es das bei allen zehn Bewertungen. An Zahlen: 4 objektive Treffer und 8
KI-Bewertungen ergeben denselben Score **0,80**, aber die Konfidenz **0,63**
gegen **0,33**.

Die Schwierigkeit kommt aus dem Ereignis (`payload.difficulty`, neu und
optional) und wird nie geraten; fehlt sie, gilt 0,5.

### Die Ankerpflicht

Weiterschaltung verlangt Score **und** `minObjectiveAnchors` objektive Anker.
Ein Score von 0,99 aus lauter KI-Bewertungen kommt nicht durch. Der Schutz
gegen R3 sitzt bewusst nicht in einer hohen Schwelle — die ließe sich mit genug
freundlichen Modellurteilen erreichen —, sondern in einer Bedingung, die ein
Sprachmodell gar nicht erfüllen kann.

Deshalb wurde die Schwelle von 0,8 auf **0,75** gesenkt (Migration `0009`):
Mit Prior und Asymmetrie erreicht 0,8 erst, wer vier saubere objektive Treffer
hinlegt — zusammen mit der Ankerpflicht doppelt gemoppelt.

### Übergangszustand (Scope-Delta 2)

Nur **16 der 168 Konzepte** haben ein freigegebenes Chart. Für die übrigen 152
sind chart-verifizierbare Anker gar nicht erreichbar. Ermittelt wird das aus
`concept_chart` × `range_chart.state = 'approved'` — nicht geraten, nicht fest
verdrahtet.

Dann treten **Ersatzanker** an die Stelle der objektiven: Signale, die nicht von
einem Modell stammen. Drei Eigenschaften, alle drei nötig:

1. keine Blockade — der Lernpfad bleibt begehbar;
2. keine stillschweigende Gleichbehandlung — das Ergebnis heißt
   `mastered_without_objective_anchors`, und die Konfidenz bleibt niedrig;
3. keine Weiterschaltung allein auf KI-Bewertungen — eine reine Serie von
   Modellurteilen scheitert an `insufficient_substitute_anchors`.

**Der Übergang endet von selbst.** Wird ein Chart freigegeben, kippt
`objectiveAnchorsPossible`, und für dieses Konzept gilt wieder die volle
Anforderung — ohne Codeänderung.

### Begründungsbausteine

`AdvanceDecision` liefert strukturierte Angaben, **keine fertigen Sätze**:
`allowed`, `reason`, `blockers`, `score`/`threshold`,
`storedConfidence`/`confidence`/`daysSinceLastCheck`,
`objectiveAnchors`/`requiredObjectiveAnchors`/`objectiveAnchorsPossible`/
`substituteAnchors` und `signalCounts`. Die Formulierung ist Sache von AP6 —
stünde hier Text, verwüchsen Logik und Wortlaut.

### Determinismus, zum Zweiten

Zwei Stellen, an denen die Regel aus T4.2 leicht zu brechen gewesen wäre:

- Die **zeitliche Gewichtung** misst gegen das jüngste Ereignis des Stroms,
  nicht gegen die Uhr.
- Die **Veralterung der Konfidenz** ist keine Ableitung, sondern Teil der
  Abfrage (`asOf`-Argument).

Zusätzlich werden gespeicherte Kennwerte auf sechs Nachkommastellen gerundet:
Gleitkomma-Addition ist nicht assoziativ, und der Replay-Vergleich soll nicht
an der letzten Stelle scheitern.

## 9. Was nach T4.4 existiert

Die zweite der vier Ableitungen hat ihre endgültige Form — wieder an derselben
Schnittstelle, wieder ohne den Service anzufassen.

| Baustein                                       | Ort                                    |
| ---------------------------------------------- | -------------------------------------- |
| SM-2-Schritt, Ursprung, Priorisierung (rein)   | `apps/backend/src/learning/review.ts`  |
| Verdrahtung (Strom → Zustandsautomat)          | `apps/backend/src/learning/derive.ts`  |
| Abruf `dueReviews`, Vorschau `upcomingReviews` | `apps/backend/src/learning/service.ts` |
| Abruf-Vertrag für AP5/AP7/AP8/AP9              | `packages/shared/src/learning.ts`      |

### Das Verfahren

```
  Ease-Änderung:  Δ = 0,1 − 0,4·x − 0,5·x²        mit x = 1 − outcome
  Wachstum:       g = 1 + (Ease − 1) · Signalgewicht
```

Die Ease-Formel ist **SM-2s eigene Parabel**, nur von `q ∈ [0,5]` auf
`outcome ∈ [0,1]` umparametrisiert. Keine erfundene Umrechnung: Die
Stützstellen stimmen exakt (1,0 → +0,10; 0,8 → 0,00; 0,6 → −0,14; 0,0 → −0,80).
Damit ist nur die Achsentransformation zu verteidigen, und die kann jeder
nachrechnen ([ADR-0043](../DECISIONS.md)).

Intervalle über objektive Erfolge: **1, 6, 17, 49, 147, 365** Tage bei Ease
2,6 → 2,7 → 2,8 → 2,9 → 3,0 → 3,0. Ease-Grenzen 1,3 bis 3,0 — dieselben Zahlen,
die seit T4.1 als CHECK-Constraint in der Datenbank stehen.

### Rückfall in zwei Fällen

| Fall                                            | Intervall | Nächste Fälligkeit      |
| ----------------------------------------------- | --------- | ----------------------- |
| **Echter Rückfall** (`repetitions ≥ 1`)         | 0         | `occurredAt + 1 Stunde` |
| Fehlschlag in der Lernphase (`repetitions = 0`) | 1 Tag     | `occurredAt + 1 Tag`    |

Die Unterscheidung ist der Kern: Wer ein sicher geglaubtes Konzept falsch
beantwortet, sieht es in derselben Sitzung wieder — sonst verfestigt sich der
Fehler. Wer ein Konzept zum ersten Mal sieht und es nicht kann, hat keinen
Rückfall, er lernt gerade; ihn im Stundentakt zu behelligen hilft niemandem.

Wiederholte Rückfälle senken den Ease dauerhaft: 2,50 → 2,18 → 1,86 → 1,54 →
1,30. Ein Erfolg bringt höchstens +0,1 zurück.

### Was die Queue ehrlich macht

Drei Ursprünge, alle aus dem Ereignisstrom abgeleitet:

| `origin`           | Bedingung                                                       |
| ------------------ | --------------------------------------------------------------- |
| `error`            | jüngster Fehlschlag aus Übung, Theorie, Journal oder Korrektur  |
| `practice_finding` | jüngster Fehlschlag aus `hand_analysis` oder `tournament` (AP8) |
| `knowledge_gap`    | kein Fehlschlag, aber **kein einziges objektives Signal**       |

Der dritte schließt den Kreis zu T4.3: Wer weitergeht, obwohl der Stand nur auf
Modellurteilen beruht (`mastered_without_objective_anchors`), bekommt das
Konzept später wieder vorgelegt. Die adaptive Weiterschaltung ist damit keine
Nachlässigkeit, sondern eine Stundung.

`knowledge_gap` ist bewusst über das **Fehlen objektiver Signale** definiert und
nicht über den Abstand zur Mastery-Schwelle: Die Schwelle ist Konfiguration,
und T4.3 hat sie ausdrücklich aus dem gespeicherten Zustand herausgehalten.
Die zweite Hälfte („nur knapp über der Schwelle") fließt über die Priorisierung
ein — niedrigere Mastery zuerst.

### Priorisierung und Abruf

Vier Stufen: Überfälligkeit in **ganzen Tagen** → Ursprung (`error` vor
`practice_finding` vor `knowledge_gap`) → Mastery aufsteigend → Konzept-ID.
Danach werden fällige Voraussetzungen vorgezogen.

Die Rundung auf ganze Tage ist der Punkt, der Erklärung braucht: Auf die Minute
genau zu sortieren wäre Scheingenauigkeit, und Stufe 2 käme praktisch nie zum
Tragen.

`dueReviews(db, { context, limit, asOf, topicAreas? })` **füllt nicht
künstlich auf**. Sind weniger fällig als angefordert, kommen weniger — aber
`dueTotal` sagt, wie viele es waren. Ob mit neuem Stoff ergänzt wird, ist eine
didaktische Entscheidung und gehört zu AP5 und AP9.

`asOf` ist Pflichtparameter. „Was ist jetzt fällig?" ist eine Frage der
Abfrage, nicht der Ableitung — dieselbe Trennung wie bei der
Konfidenz-Veralterung aus T4.3.

## 10. Was nach T4.5 existiert

Die letzte der vier Ableitungen hat ihre endgültige Form — und mit ihr kommt
die zweite Dimension neben dem Kapitelfortschritt.

| Baustein                                       | Ort                                             |
| ---------------------------------------------- | ----------------------------------------------- |
| Rating-EWMA, Verlaufsverdichtung (rein)        | `apps/backend/src/learning/rating.ts`           |
| Level-Kalibrierung mit Hysterese (rein)        | `apps/backend/src/learning/level.ts`            |
| Verdrahtung (Strom → Signale)                  | `apps/backend/src/learning/derive.ts`           |
| Level lesen und setzen, Ratings und Verlauf    | `apps/backend/src/learning/service.ts`          |
| Kommando `pnpm learning:level`                 | `apps/backend/src/learning/cli-level.ts`        |
| Migration (`level_set`, `concept_id` nullable) | `apps/backend/drizzle/0010_level_set_event.sql` |

### Die Rating-Formel

```
  rating₁ = outcome₁                                  (erste Beobachtung)
  ratingᵢ = ratingᵢ₋₁ + αᵢ · (outcomeᵢ − ratingᵢ₋₁)
  αᵢ = 0,15 · Signalgewicht · Schwierigkeit
```

Signalgewichte und Schwierigkeitsmaß sind **unverändert die aus T4.3**. Was
dort ein starkes Signal ist, ist es hier auch — sonst sähe der Nutzer zwei
Zahlen, die sich widersprechen. Nicht übernommen ist die Fehler-Asymmetrie: Sie
gilt einem einzelnen Konzept, ein Rating mittelt über einen ganzen
Themenbereich ([ADR-0044](../DECISIONS.md)).

Trägheit an Zahlen: Nach zwölf objektiven Treffern steht das Rating bei
**1,000**; ein einzelner Totalausfall drückt es auf **0,850** — genau um α.
Aufwärts, aus einem Start von 0,2 über zehn Treffer: **0,200 → 0,422 → 0,582 →
0,744 → 0,815**.

Die **erste** Beobachtung setzt das Rating, statt es von 0 anzuziehen: Ein
Startwert von 0 hieße zugleich „keine Daten" und „sehr schlecht". Wie belastbar
der Wert ist, sagt `eventCount`.

### Verlauf, verdichtet

`skill_rating_snapshot` hält **einen Punkt je Achse und Kalendertag**. 40
Ereignisse über zehn Tage ergeben zehn Punkte — höchstens 12 × 365 Zeilen im
Jahr statt Tausender. Die IDs sind aus Themenbereich und Tag abgeleitet
(UUIDv5), damit der Replay dieselben Zeilen erzeugt und nicht bloß inhaltlich
gleiche.

### Level: drei Stufen, Hysterese, Fixpunkt

Die Stufen sind **dieselben wie `concept.min_level`** aus T3.2:
`einsteiger`, `fortgeschritten`, `experte`. Eine vierte Lernenden-Stufe hätte
im Konzeptgraphen keine Entsprechung und wäre eine zweite Liste, die
auseinanderlaufen kann ([ADR-0045](../DECISIONS.md)).

| Stufe             | Aufstieg                                          | Halten                                            |
| ----------------- | ------------------------------------------------- | ------------------------------------------------- |
| `fortgeschritten` | Ø ≥ 0,55 · 5 Konzepte · 20 % objektiv · 2 Achsen  | Ø ≥ 0,45 · 3 Konzepte · 10 % objektiv · 1 Achse   |
| `experte`         | Ø ≥ 0,78 · 20 Konzepte · 40 % objektiv · 5 Achsen | Ø ≥ 0,68 · 15 Konzepte · 30 % objektiv · 4 Achsen |

Dazwischen liegt das **tote Band**. Die Folge 0,56 · 0,54 · 0,56 · 0,53 · 0,57 ·
0,52 · 0,55 · 0,54 pendelt genau um die Aufstiegsschwelle und erzeugt **genau
einen** Wechsel.

Der Aufstieg geht in einem Schritt bis zur höchsten getragenen Stufe: Der Start
bei `einsteiger` ist eine Vorsichtsannahme, keine Feststellung. Dass ein
einzelnes Ereignis nicht degradiert, ist keine Zusatzregel, sondern
rechnerisch — es bewegt den Durchschnitt über zwölf Achsen um wenige
Hundertstel, das Band ist zehn Hundertstel breit.

### Das erste Ereignis ohne Konzept

Die manuelle Level-Setzung läuft über ein Ereignis vom Typ `level_set`, nicht
über einen Schreibzugriff — sonst wäre sie der zweite Schreibweg, den das
Umgehungsverbot aus T4.2 ausschließt, und der Replay wüsste nichts davon.

Damit wird `learning_event.concept_id` nullable (Migration `0010`). Statt die
Invariante aus T4.1 aufzugeben, tritt ein CHECK an ihre Stelle:
`learning_event_scope_check` erzwingt, dass ein Ereignis **entweder** ein
Lernereignis an einem Konzept **oder** ein globales Ereignis am Lernenden ist.

Die Setzung gilt 30 Tage; danach greift die Automatik wieder. Während der Frist
bleibt `automaticLevel` sichtbar, damit AP6 den Unterschied anzeigen kann statt
ihn zu verschweigen.

## 11. Was nach T4.6 existiert

Der einzige KI-Aufruf in AP4 — und er steht am Ende einer Kette, die ihn
dreimal verhindern kann.

| Baustein                                          | Ort                                                |
| ------------------------------------------------- | -------------------------------------------------- |
| Aggregation, Prüfsumme, Kurzkennung (rein)        | `apps/backend/src/learning/patterns.ts`            |
| Laden, Speichern, Muster-Tags, Lesen              | `apps/backend/src/learning/report.ts`              |
| Job-Typ `learning.pattern-report`                 | `apps/backend/src/jobs/handlers/pattern-report.ts` |
| Analyse-Template                                  | `apps/backend/prompts/task/error-patterns.md`      |
| Kommando `pnpm learning:report`                   | `apps/backend/src/learning/cli-report.ts`          |
| Migration (`pattern_report`, `error_pattern_tag`) | `apps/backend/drizzle/0011_pattern_report.sql`     |

### Der Schweregrad wird abgeleitet

| Signalklasse    | Ergebnis 0 | Ergebnis zwischen 0 und 0,5 |
| --------------- | ---------- | --------------------------- |
| `objective`     | `high`     | `medium`                    |
| `ai_judged`     | `medium`   | `low`                       |
| `self_reported` | `low`      | `low`                       |

Dieselbe Rangfolge wie bei den Signalgewichten aus T4.3, und aus demselben
Grund: Ein Fehler bei einer chart-verifizierbaren Frage ist ein harter Befund.
Eine KI-Bewertung kann auch an einer unpräzisen Formulierung liegen.

### Drei Stufen vor dem Aufruf

1. **Aggregation** — deterministischer Code verdichtet das Protokoll zu
   Kennzahlen je Konzept, Themenbereich, Kontext, Woche und Schweregrad.
2. **Mindestdatenmenge** — unter **8 Fehlern** oder **3 Konzepten** kein
   Aufruf, stattdessen ein gespeicherter Hinweis.
3. **Prüfsumme** — unveränderte Fehlerlage, kein zweiter Aufruf. Das
   Zeitfenster geht bewusst nicht ein.

Die wichtigste Kennzahl ist `repeatedAfterReview`: Fehler **nach** einer
zwischenzeitlich gelungenen Wiederholung. Drei Fehler am Stück heißen „noch
nicht gelernt". Ein Fehler nach einem Erfolg heißt: Es saß schon einmal und ist
wieder gekippt.

### Was der Live-Lauf verbessert hat

Der Live-Lauf war nicht nur eine Abnahme, sondern hat **zwei echte Mängel
gefunden** — beide behoben und mit Tests abgesichert:

- **Trend-Label.** Die Reihe 0-3-2-3-1 wurde als `worsening` gemeldet, obwohl
  die letzte Woche die beste war. Die führende Null-Woche zog den Vergleich der
  ersten Hälfte nach unten. Leere Wochen **vor** dem ersten Fehler fallen jetzt
  heraus; Lücken **zwischen** Fehlern bleiben, denn die sind eine Auskunft.
- **Muster-Tags.** Ein breites Muster („durchgängig hoher Schweregrad", alle
  drei Konzepte) zog alle Einträge an sich, und das aussagekräftige
  („wiederkehrende Fehler bei X und Y") blieb leer. Zugeteilt wird jetzt nach
  **Spezifität**: das Muster mit den wenigsten genannten Konzepten zuerst.

Das Modell hat den ersten Punkt selbst gemeldet, als Muster mit `vertrauen:
'niedrig'` — genau das Verhalten, das die Analyse-Persona verlangt.

### Muster-Tags stehen neben dem Protokoll

`error_log` ist eine Projektion und wird bei jedem neuen Ereignis des Konzepts
neu aufgebaut — ein direkt hineingeschriebener Tag wäre beim nächsten
Schreibvorgang weg und nach einem Replay ohnehin. Die Zuordnung liegt deshalb
in `error_pattern_tag`; `error_log.pattern_tag` ist ihre Spiegelung und
überlebt damit beides ([ADR-0046](../DECISIONS.md)).

### Der Report verändert keinen Lernstand

Mastery, Queue, Ratings und Level bleiben deterministisch berechnet. Der Report
schreibt nach `pattern_report` und `error_pattern_tag`, sonst nirgends. Hier
verläuft die Linie zwischen deterministischem Kern und KI am Rand — an der
Stelle, an der sie am meisten in Versuchung führt.

### Wöchentlich ohne Scheduler

Jeder Lauf plant seinen Nachfolger sieben Tage später in die Job-Queue aus AP2
ein; steht dort schon einer, passiert nichts. Fällt der Worker aus, läuft der
Report später — nicht mehrfach.

## 14. Offene Punkte und Risiken

- **Die Ereignis-ID hat keinen Default.** Das ist Absicht ([ADR-0037](../DECISIONS.md)):
  Ein Aufrufer, der sie vergisst, soll scheitern statt still ein Duplikat zu
  erzeugen. T4.2 muss sie folglich immer setzen.
- **`TRUNCATE` ist vom Append-only-Trigger nicht abgedeckt** — bewusst, weil der
  Neuanfang genau darauf aufsetzt (ADR-0039). Nebenwirkung: Ein
  `TRUNCATE … CASCADE` auf `concept` oder `book_chapter` reißt den Lernstand
  mit. Das betrifft nur Test- und Entwicklungspfade.
- **Die Kanon-Datei liegt als `docs/ap/AP04 (1).md` im Repo, nicht als
  `docs/ap/AP04.md`,** und ist nicht committet. Inhaltlich stimmt sie mit dem
  Auftrag überein; `docs/ap/` wird vom Agenten nicht angefasst (Regel 6). Zu
  erledigen vom Nutzer.
- Der Rating-Wertebereich ist auf 0–1 festgelegt (CHECK), analog zum
  Mastery-Score. Sollte die EWMA in T4.5 eine andere Skala brauchen, ist das
  eine zusätzliche Migration.
- **Die Ankerpflicht läuft derzeit fast überall über Ersatzanker.** Bei 16 von
  168 Konzepten mit freigegebenem Chart ist der Übergangszustand aus
  Scope-Delta 2 der Regelfall, nicht die Ausnahme. Der Schutz gegen R3 ist
  dadurch schwächer als vorgesehen — ein Ersatzanker ist eine
  Selbsteinschätzung, kein objektiver Beleg. Das löst sich erst mit der
  Chart-Digitalisierung (RUNBOOK 13), nicht im Code.
- Die Halbwertszeit von 30 Tagen ist gesetzt, nicht gemessen. Sie lässt sich
  ohne Datenverlust ändern: Konstante anpassen, `pnpm learning:replay` — die
  Ereignisse bleiben.
- `payload.difficulty` ist optional und wird von noch keinem Modus gesetzt;
  bis AP5/AP7 sie liefern, rechnet alles mit mittlerer Schwierigkeit.
- **Ein Konzept ohne Fehlschlag und mit objektiven Belegen steht nicht in der
  Queue.** Turnusmäßige Wiederholung ohne Anlass ist in AP4 nicht vorgesehen —
  die Ursprungsliste aus T4.1 kennt nur Fehler, Lücke und Praxisbefund. Sollte
  AP5 sie wollen, ist der Weg ein `review_performed`-Ereignis oder ein vierter
  Ursprung, dann aber als eigene Entscheidung.
- Die Rückfall-Wartezeit von einer Stunde und der Intervall-Deckel von einem
  Jahr sind gesetzt, nicht gemessen. Beide lassen sich ohne Datenverlust
  ändern: Konstante anpassen, `pnpm learning:replay`.
- Der Kontext (`session`/`drill`/`tournament`) filtert derzeit nicht; er wird
  in der Antwort gespiegelt und über `topicAreas` bedient. Die
  turnierspezifische Auswahl ist ausdrücklich AP8.
- **Das Level hat drei Stufen, nicht die im Task beispielhaft genannten vier.**
  Die Begründung steht in ADR-0045 (keine zweite Liste neben
  `concept.min_level`); der Kanon nennt keine Stufenzahl. Wer vier will, braucht
  eine Migration am CHECK aus T4.1 **und** eine Abbildung auf die
  Konzept-Level — das sollte eine bewusste Entscheidung sein.
- **Die erste Beobachtung setzt das Rating einer Achse.** Eine einzelne
  Selbsteinschätzung kann eine Achse damit kurzzeitig auf einen hohen Wert
  heben. Sichtbar bleibt das über `eventCount = 1`, und das zweite Ereignis
  zieht es schon wieder — aber die Anzeige in AP6 sollte `eventCount` neben dem
  Rating zeigen, nicht nur den Wert.
- **`objectiveShare ≥ 0,40` für `experte` ist beim aktuellen Datenstand schwer
  erreichbar.** Nur 16 von 168 Konzepten haben ein freigegebenes Chart; ein
  hoher Anteil objektiver Signale setzt viele chart-verifizierbare Fragen
  voraus. Dasselbe Thema wie bei der Ankerpflicht in T4.3 — es löst sich mit
  der Chart-Digitalisierung, nicht im Code.
- **Ein Replay rechnet auch den Verlauf neu.** Alte Punkte spiegeln danach die
  aktuelle Formel, nicht die, die damals galt. Der Verlauf ist eine
  Neuberechnung der Geschichte, kein Archiv (RUNBOOK 16.15).
- **Der Muster-Report deutet, er misst nicht.** Eine falsche Deutung ist
  möglich und kostet Aufmerksamkeit, keine Daten — er verändert keinen
  Lernstand. Was zu tun ist, wenn ein Muster danebenliegt, steht in
  RUNBOOK 16.18.
- **Die Muster-Zuteilung folgt der Spezifität, nicht der Tragweite.** Ein
  Ereignis gehört zu höchstens einem Muster; zugeteilt wird an das Muster mit
  den wenigsten genannten Konzepten. Nennen zwei Muster dieselbe Konzeptmenge,
  entscheidet die Reihenfolge des Modells. Für eine bessere Regel bräuchte es
  eine Zuordnung Muster → Ereignis aus dem Modell selbst — das wäre eine
  Erweiterung des Antwortschemas.
- **Der Live-Lauf ist bewusst kein Teil von `pnpm test`.** Er kostet Kontingent
  und braucht den Host-Runner. Wer die Muster fachlich prüfen will, startet ihn
  von Hand (`LLM_LIVE_SMOKE=true`).
- Die wöchentliche Kette lebt davon, dass jeder Lauf seinen Nachfolger einplant.
  Landet ein Job im Dead-Letter, reißt sie ab — sichtbar über die Abfrage in
  RUNBOOK 16.16, wieder in Gang zu setzen mit `pnpm learning:report --run`.
